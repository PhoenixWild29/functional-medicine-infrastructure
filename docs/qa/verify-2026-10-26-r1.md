## V1. Medium: a GET after a 303 (or a 301 / 302 after a POST) still sends the form body

- **Where:** `src/lib/adapters/transmission-guard.ts:369` on c9cc9ec1:

  ```ts
  route.fetch({ url, method, headers, maxRedirects: 0, ...(postData !== undefined ? { postData } : {}) })
  ```

  When the chain turns into a GET, `postData` is `undefined`, so the option is left out.
  - **Playwright's `route.fetch` then reuses the intercepted request's original post data.** An omitted option means "the request's own", not "no body".
  - So the GET carries the PHI form body to the redirect target.
- **Confirmed in Chromium.** A form POST to `/post-ok` went `307 -> /post-ok2`, then `303 -> /done`. The server received `GET /done body=x=1` (3 of 3 runs). A browser sends that GET with no body.
- **Effect:**
  - An https portal that redirects a submit with a 303 sends the typed patient and prescription fields again, in the body of a GET, to the 303's target.
  - The target is https (the rule still holds) but may be another origin, and the browser would never have sent it the body there.
  - This is not cleartext, which is why it is Medium and not High. But it sends PHI to a place the browser never would.
  - The same applies to the status poll's typed credentials.
- **Why C's test passes:** the scripted case checks the options handed to the mocked `route.fetch`, which carry no `postData`. It cannot see Playwright's default.
- **Fix (one line, checked):** always pass the body, empty when the request has become a GET:

  ```ts
  route.fetch({ url, method, headers, maxRedirects: 0, postData: postData ?? Buffer.alloc(0) })
  ```

  - With that change, the same probe gives `GET /done body=` (empty).
  - The 307 hops still carry their body, and both R1 chains stay closed.
  - Add to the Chromium test: `POST -> 307 -> 303 -> same origin`, and assert that the final GET has an empty body.

## Design notes (no finding)

- **`page.url()` stays the first URL of the chain.** The final answer is fulfilled as the response to the first request, so relative links and form actions on that page resolve against the first URL.
  - That is what B's fix proposed, and it is safe.
  - But a portal whose flow depends on landing on a different path after a redirect (for example `/login -> /dashboard` with relative links) could behave differently.
  - Watch the first real Tier 2 portal run.
- **Cookies.**
  - `route.fetch` uses the context's cookie store, so cookies set on intermediate hops are stored under their own origins.
  - Any `Set-Cookie` on the final answer is also applied by the browser to the first URL's host, because that is the response it sees.
  - This matters only for a chain that ends on another origin. Low; noted.
- **`serviceWorkers: 'block'`** is right: a context route does not see what a service worker answers.
